O que é um Sistema Operacional?

O programa que você nunca abriu, nunca instalou conscientemente e nunca fechou — mas que está rodando agora, em cada aparelho seu, mediando absolutamente tudo.

Ponto de partida

Hardware sozinho não faz nada

📖 Tanenbaum & Bos — Sistemas Operacionais Modernos, 4ª ed., p. 1
"Se todo programador de aplicativos tivesse de compreender como todas essas partes funcionam em detalhe, nenhum código jamais seria escrito."

Um computador moderno é um amontoado de peças que não se conhecem: processadores, memórias, discos, teclado, placa de rede, GPU. Cada uma com seu próprio jeito de ser controlada, seus registradores, seus tempos. Alguém precisa colocar ordem nisso.

🧱 Programas de sistema

  • Operam o próprio computador
  • Sistema operacional, drivers, compiladores
  • Só o SO roda em modo núcleo — acesso total ao hardware. Compiladores e shell rodam em modo usuário, como qualquer aplicativo
×

📱 Programas aplicativos

  • Resolvem o problema do usuário
  • Navegador, editor, jogo, seu programa em C
  • Rodam em modo usuário — acesso restrito, pedem tudo ao SO

O SO é o programa de sistema mais básico: controla os recursos da máquina e fornece a base sobre a qual os demais programas são escritos.

Os dois papéis do SO

Duas visões da mesma coisa

🎁

1. Máquina estendida (visão de cima para baixo)

O SO esconde a feiura do hardware e oferece ao programador uma máquina mais simples de programar, feita de abstrações limpas: arquivos, processos, memória. Você chama read() e não quer saber de prato, cilindro e trilha.

👮

2. Gerente de recursos (visão de baixo para cima)

O SO arbitra a disputa: dezenas de programas querem CPU, memória, disco e rede ao mesmo tempo. Ele decide quem usa o quê, quando e por quanto tempo — e impede que um invada o outro.

💡 Guarde estes dois nomes
Máquina estendida e gerente de recursos são as duas metades da resposta para "o que faz um SO?". Toda unidade desta disciplina vai ser uma das duas — ou as duas ao mesmo tempo.

Papel 1 — Máquina estendida

Ler um dado do disco

😱 Sem sistema operacional

  • Descobrir prato, cilindro, trilha e setor
  • Ligar o motor e esperar o eixo estabilizar
  • Posicionar a cabeça de leitura/escrita
  • Aguardar o setor certo passar sob a cabeça
  • Ler os bytes, tratar erro de CRC, remontar o dado
  • E refazer tudo para cada modelo de disco
→

😌 Com sistema operacional

  • fd = open("dados.txt")
  • read(fd, buffer, 100)
  • close(fd)
  • Funciona igual em HD, SSD, pendrive ou disco de rede.
💡 A analogia do carro
Dirigir não exige entender injeção eletrônica nem sincronismo de válvulas: volante, pedais e câmbio são a abstração que o carro oferece. O SO faz o mesmo com o hardware — arquivos em vez de setores, processos em vez de registradores, memória virtual em vez de endereços físicos.

Papel 2 — Gerente de recursos

Quem usa o quê, e quando?

Abra o gerenciador de tarefas agora: centenas de processos "rodando ao mesmo tempo" em um punhado de núcleos. Eles não rodam ao mesmo tempo — se revezam tão rápido que a ilusão é perfeita. Quem organiza o revezamento é o SO.

⏱️Multiplexação no tempo — a CPU e a impressora são usadas por um programa de cada vez, em turnos. Quem decide a ordem é o escalonador.
📦Multiplexação no espaço — a memória e o disco são divididos em pedaços simultâneos, cada programa com o seu.
🛡️Proteção — o SO impede que um programa leia ou corrompa a memória do outro. Sem isso, um bug em um aplicativo derrubaria a máquina inteira.
🔥 O SO é um programa "preguiçoso"
Enquanto você lê este slide, o SO está, na maior parte do tempo, parado. Ele só acorda quando o hardware o interrompe (pacote de rede, timer) ou quando um programa lhe pede algo.
💡 Ligação com a próxima aula
Esse "pedir algo ao SO" tem nome — chamada de sistema — e é a fronteira exata entre o seu código e o kernel. Chegaremos lá na Aula 04.

As três peças

🎭

Virtualização

Transformar um recurso físico em muitos virtuais: uma CPU vira "uma CPU por processo"; a RAM vira "uma memória por programa".

🔀

Concorrência

Várias linhas de execução mexendo nas mesmas coisas ao mesmo tempo dão errado de formas assustadoras. Como coordenar sem travar tudo?

Persistência

Memória some quando falta energia. Como guardar dados de forma durável num dispositivo lento e sujeito a falhas?

Fonte: Projeto Pedagógico do Curso — TADS/IFRN

Traduzindo: o objetivo não é você decorar como o Linux funciona por dentro. É você se tornar um desenvolvedor que entende o chão em que pisa — que sabe por que o programa está lento, por que ele consome 4 GB de RAM, por que o teste passa na sua máquina e falha na do colega, e por que aquele bug só aparece "às vezes".

💡 O diferencial no mercado
Praticamente todo desenvolvedor sabe escrever um loop. Poucos sabem explicar por que o servidor caiu sob carga, o que é um deadlock ou por que o container estourou o limite de memória. É aí que essa disciplina paga o investimento.

O que é um container, de verdade

Máquina virtual × container

📦 Máquina virtual
seu programa em C
bibliotecas do Ubuntu
kernel Linux completo — mais um SO inteiro na memória
hipervisor (VirtualBox / VMware)
SO do seu computador
hardware

Dois sistemas operacionais empilhados. Liga em ~40 s.

🐳 Container
seu programa em C
bibliotecas do Ubuntu
kernel compartilhado — namespaces + cgroups isolam
SO do seu computador
hardware

Um kernel só. Liga em ~0,3 s.

Um container não é uma máquina: é um punhado de processos comuns do seu Linux, que o kernel enganou. Para eles, o PID 1 é o bash, a raiz do sistema de arquivos é a imagem do Ubuntu, e não existe nenhum outro processo no mundo. É isolamento, não emulação — por isso é instantâneo.

O limite da técnica

Container só roda Linux sobre Linux

Container usa o kernel do hospedeiro — logo, só roda Linux sobre Linux. No Windows e no macOS o Docker Desktop mantém, escondida, uma pequena máquina virtual Linux e coloca os containers dentro dela. Você não a vê nem a administra, mas ela está lá: num Mac ou num PC com Windows você tem VM e container.

🪟 Em Windows e macOS

  • A VM é uma só, minúscula e mantida pela Docker — você nunca a instala nem a atualiza
  • O kernel lá dentro é Linux de verdade: fork, ptrace e IPC System V funcionam como na prova
  • Trocar de ambiente custa um comando, não uma reinstalação
×

🐧 Em um hospedeiro Linux

  • Nenhuma VM no meio: o container é processo direto do seu kernel
  • ps na máquina de fora mostra os processos do container, com outro PID
  • É o caso das máquinas do laboratório do IFRN

O vocabulário — quatro palavras que se confundem

Dockerfile, imagem, container e volume

📜

Dockerfile

Arquivo de texto que descreve o ambiente: qual Linux, quais programas, onde começar. É o que se versiona e compartilha.

💿

Imagem

O ambiente já construído (docker build): um sistema de arquivos congelado, somente leitura. Construída uma vez, usada muitas.

🏃

Container

Uma execução da imagem (docker run). Nasce, roda, termina. O que um altera não afeta os outros.

🔗

Volume

-v espelha uma pasta sua dentro do container. Você edita no VS Code; o GCC lá dentro lê o arquivo alterado.

💡 Analogia
Dockerfile está para imagem como código-fonte está para executável. E container está para imagem como processo está para programa em disco — a mesma distinção que a Unidade 2 vai formalizar.

Passo 6 de 6 — verificação do ambiente

Compilar e rodar o primeiro programa

💻 teste.c no seu PC
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>
int main(void) {
    pid_t f = fork();
    if (f == 0)
        printf("Sou o FILHO (PID %d)\n", getpid());
    else {
        wait(NULL);
        printf("Sou o PAI   (PID %d), filho = %d\n",
               getpid(), f);
    }
    return 0;
}
so:/so$ gcc -Wall -g -o teste teste.c so:/so$ ./teste Sou o FILHO (PID 12) Sou o PAI (PID 11), filho = 12 so:/so$ strace -e trace=clone,write ./teste clone(..., flags=...|SIGCHLD, ...) = 12 Sou o FILHO (PID 12) write(1, "Sou o PAI (PID 11)"..., 33) = 33 so:/so$ man 2 fork fork(2) System Calls Manual fork(2)
💡 PID 11 e PID 12?
Fora do container esses PIDs teriam cinco dígitos. O container tem seu próprio namespace de PID: ali a numeração recomeça do 1.

O Dockerfile completo

📜 so-lab/Dockerfile sem extensão · D maiúsculo
# Sistemas Operacionais — TADS/IFRN 2026.1 · docker build -t so-ifrn .

FROM ubuntu:24.04

# O Ubuntu base vem sem páginas de manual. Removendo esta
# regra ANTES do apt-get, o "man 2 fork" passa a funcionar.
RUN rm -f /etc/dpkg/dpkg.cfg.d/excludes

# Sem isto, alguns pacotes param esperando o fuso e travam.
ENV DEBIAN_FRONTEND=noninteractive
ENV TZ=America/Fortaleza
ENV LANG=C.UTF-8

RUN apt-get update && apt-get install -y \
      --no-install-recommends \
      build-essential gdb valgrind libomp-dev \
      strace ltrace procps psmisc htop time \
      python3 nano vim less \
      man-db manpages manpages-dev \
      manpages-posix manpages-posix-dev \
      file tree bsdextrautils \
 && rm -rf /var/lib/apt/lists/*
# A imagem base desvia /usr/bin/man para um aviso de
# "sistema minimizado". Desfeito o desvio, o man-db
# recém-instalado volta a ser o man de verdade.
RUN rm -f /usr/bin/man \
 && dpkg-divert --quiet --remove --rename /usr/bin/man

# Prompt verde "so:" — assim você sempre sabe que está
# DENTRO do container. O ~/.bashrc do root é lido depois
# do /etc/bash.bashrc e redefiniria o prompt, por isso o
# tee grava nos dois arquivos.
RUN printf '%s\n' \
    "export PS1='\[\e[1;32m\]so\[\e[0m\]:\w\$ '" \
    "alias ll='ls -lh --color=auto'" \
    "alias cc='gcc -Wall -Wextra -g'" \
    | tee -a /etc/bash.bashrc >> /root/.bashrc

# /so é a pasta do seu computador, montada aqui dentro.
WORKDIR /so
CMD ["/bin/bash"]

Arquivo 2 de 2 — o atalho

O script so.sh

⚙️ so-lab/so.sh Linux e macOS · versão essencial
#!/usr/bin/env bash
# Atalho do laboratório de SO — TADS/IFRN 2026.1
# ./so.sh [build | run x.c | limpar]
set -euo pipefail

IMAGEM="so-ifrn"
PASTA="$(cd "$(dirname "$0")" && pwd)"

# -it  terminal interativo
# --rm descarta o container ao sair
# -v   espelha esta pasta em /so
# as duas últimas liberam o ptrace(), sem o qual
# gdb e strace não funcionam aqui dentro
FLAGS=( -it --rm -v "$PASTA":/so
        --cap-add=SYS_PTRACE
        --security-opt seccomp=unconfined
        --name so-lab )
# Constrói a imagem se ela ainda não existir.
docker image inspect "$IMAGEM" >/dev/null 2>&1 \
  || docker build -t "$IMAGEM" "$PASTA"

case "${1:-shell}" in
  build)  docker build -t "$IMAGEM" "$PASTA" ;;
  shell)  docker run "${FLAGS[@]}" "$IMAGEM" ;;
  run)    BIN="${2%.*}"
          docker run "${FLAGS[@]}" "$IMAGEM" bash -c \
            "gcc -Wall -Wextra -g -pthread -fopenmp \
              -o $BIN $2 && ./$BIN" ;;
  limpar) docker rmi -f "$IMAGEM" ;;
  *)      echo "use: build | shell | run | limpar"
          exit 1 ;;
esac

A versão completa — com checagem do Docker, o subcomando exec e o mapeamento de usuário no Linux — vem no material, junto com o so.ps1 para Windows.

🔥 O que essa diferença revela
Dentro do container o ps aux lista dois ou três processos. Fora, trezentos — e ambos rodam sobre o mesmo kernel, na mesma máquina. A lista de processos, portanto, não é um fato do hardware: é uma visão que o kernel constrói para cada namespace. É esse mecanismo que a Unidade 2 detalha.
